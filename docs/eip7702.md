# EIP-7702 trading account

`src/TradingAccount7702.sol` is a delegation implementation for an existing EOA.
Deploy it once per supported chain, then have the user's wallet authorize that
implementation through an EIP-7702 transaction. Calls execute at the user's
address and use ordinary `CALL` to reach the markets. Their `msg.sender` remains
the user's EOA, so USDC, positions, LP shares, and payouts stay at that address.
Adding delegation itself does not require market redeployment. Migrating to the
new options lifecycle does require redeploying OptionsAMM and opUSDC as described
in [options integration](options.md).

This is an account executor, not a new trading venue or a trusted-forwarder
router. The markets continue to enforce their existing oracle, collateral,
slippage, and ownership checks. There is no backend trading permission, session
key, ERC-4337 EntryPoint integration, or relayer reimbursement in this contract.

## Deploy and test

Configure `PRIVATE_KEY`, `RPC_URL`, and `CHAIN_ID` in a shell-compatible `.env`
file, then use the deployment runner from macOS, Linux, or Git Bash on Windows:

```bash
# Simulate without broadcasting.
bash script/deploy/deploy-trading-account-7702.sh .env --dry-run

# Deploy after interactive confirmation.
bash script/deploy/deploy-trading-account-7702.sh .env

# Deploy without prompting, optionally with a different environment file.
bash script/deploy/deploy-trading-account-7702.sh .env.testnet --yes
```

The runner accepts Windows line endings, checks the RPC chain ID and deployer
balance, and uses the existing Solidity 0.8.20 deployment profile. Save the
printed implementation address as `TRADING_ACCOUNT7702_ADDRESS` in your local
environment file. It does not require a Pyth address or existing market addresses.

Alternatively, export the environment variables and invoke Foundry directly:

```bash
forge script script/DeployTradingAccount7702.s.sol:DeployTradingAccount7702 \
  --rpc-url "$RPC_URL" --broadcast
```

The script reads `PRIVATE_KEY` from the process environment, like the other
Foundry scripts. Deploying the implementation does not delegate any wallet.
Use the printed address as `implementation` below. Verify with:

```bash
forge verify-contract <IMPLEMENTATION_ADDRESS> \
  src/TradingAccount7702.sol:TradingAccount7702 \
  --chain <CHAIN_ID> --num-of-optimizations 1 --via-ir --watch
```

Use an EIP-7702-capable network, RPC, and wallet; an implementation deployment
on its own does not demonstrate that the network supports type-4 transactions.
The [EIP-7702 specification](https://eips.ethereum.org/EIPS/eip-7702) defines
delegation and the separate authorization-list nonce.

The new integration and security tests live in `test7702/`. The separate
profile uses Solidity 0.8.30 and Prague for real delegation cheatcodes, as
required by [Foundry's delegation documentation](https://getfoundry.sh/reference/cheatcodes/sign-delegation).
It has separate artifact and cache directories so the market deployment
compiler settings stay unchanged:

```bash
forge test                         # Existing protocol regression tests
FOUNDRY_PROFILE=eip7702 forge test -vv
```

PowerShell:

```powershell
$env:FOUNDRY_PROFILE = 'eip7702'
forge test -vv
Remove-Item Env:FOUNDRY_PROFILE
```

`test7702/fixtures/batch.json` is an independent EIP-712 reference vector.
The tests execute its Cast-generated signature, checking interoperability with
standard typed-data signing in addition to the contract's digest helper.

## Build a batch

Each call is `(address target, uint256 value, uint256 gasLimit, bytes data)`.
`value` is native currency in wei; the other amounts use the existing market
units. `gasLimit` is a positive per-call gas allowance, not the transaction's
total gas. Budget total transaction gas for every call plus validation,
storage, return data, and EIP-150 overhead; estimate before submitting.

| Market | Example atomic calls | USDC approval amount |
| --- | --- | --- |
| PerpDex | `USDC.approve(perp, margin)` then `perp.openPosition(...)` | Position margin |
| PredictionMarketAMM | `USDC.approve(prediction, assets)` then `prediction.buy(...)` | Bet stake |
| OptionsAMM | `USDC.approve(options, premium)` then `options.buy(...)` | Quoted premium |

You can combine all three sequences into one six-call batch. Approve each
market directly as spender, using the exact amount rather than unlimited
allowances. For tokens that require clearing an existing allowance first,
prepend an `approve(spender, 0)` call. The executor uses raw `CALL`: an ERC-20
returning `false` without reverting does not itself abort the batch; the
following market transfer checks still enforce a successful purchase with the
supported USDC. Do not assume arbitrary token calls have SafeERC20 semantics.

Fetch real Pyth update payloads before signing. Assign the correct
`pyth.getUpdateFee(priceUpdateData)` to each payable market call's `value`.
The account can use its existing native balance plus signed sponsor funding.
Unused funding stays in the EOA. Options buys and sells both require a fresh
Pyth update and the corresponding native oracle fee.

For prediction trades, retain `minShares` and the market deadline in calldata.
For options buys, retain `maxPremium`; sells use `minProceeds`. Both include
the normalized current price and a trade deadline. The account-level deadline adds another
expiration check. PerpDex's existing open interface has no separate price
slippage parameter; delegation does not introduce one.

LP deposit/withdrawal, PerpDex closing and TP/SL edits, option sales, and
prediction opening/resolution can also be encoded using their existing ABIs.
Prediction winners are paid automatically on resolution; there is no claim call.
Options backends finalize rounds with `finalizeMarket`, automatically paying
remaining holders to their EOAs. The owner authorizes the backend separately;
delegation does not grant backend permissions. See [options integration](options.md).

## Self-paid execution

Send the transaction **from the EOA to itself**, with `execute(calls)` as data.
An external caller cannot use `execute`. For the first transaction, include a
wallet-authorized EIP-7702 authorization list pointing to the implementation.
Delegation persists across transactions; later batches can omit that list.

With Viem clients configured for the target chain, and `owner` a LocalAccount:

```ts
import { encodeFunctionData, parseAbi } from 'viem'

const accountAbi = parseAbi([
  'function execute((address target,uint256 value,uint256 gasLimit,bytes data)[] calls) payable returns (bytes[] results)',
  'function executeSigned((address target,uint256 value,uint256 gasLimit,bytes data)[] calls,uint256 batchNonce,uint256 deadline,address relayer,bytes signature) payable returns (bytes[] results)',
  'function nonce() view returns (uint256)',
])

// calls is the ordered array described above. The owner supplies native fees.
const authorization = await ownerClient.signAuthorization({
  account: owner,
  contractAddress: implementation,
  executor: 'self',
})
const hash = await ownerClient.sendTransaction({
  account: owner,
  to: owner.address,
  authorizationList: [authorization],
  data: encodeFunctionData({ abi: accountAbi, functionName: 'execute', args: [calls] }),
})
```

`executor: 'self'` handles the EOA transaction-nonce increment before the
authorization is processed. A sponsored authorization omits it, following
[Viem's signAuthorization documentation](https://viem.sh/docs/eip7702/signAuthorization).
Use the appropriate wallet's supported authorization flow for a browser wallet.

## Sponsored execution

The user signs **two different authorizations** on first use:

1. The EIP-7702 authorization selects code for the account. It does not sign a trade.
2. An EIP-712 `Batch` signature authorizes the exact calls submitted to `executeSigned`.

Subsequent sponsored batches need only the EIP-712 signature while delegation
remains installed. The sponsor pays transaction gas and sends exactly the
signed `funding` as transaction value. There is no USDC gas charge.

Continue the Viem example with `publicClient`, `ownerClient`, and `sponsorClient`
on the same chain; `sponsor` is the sponsor's LocalAccount:

```ts
import { padHex } from 'viem'

const chainId = await publicClient.getChainId()
const code = await publicClient.getCode({ address: owner.address })
const expectedCode = ('0xef0100' + implementation.slice(2)).toLowerCase()
if (code && code !== '0x' && code.toLowerCase() !== expectedCode) {
  throw new Error('Review the existing delegation before replacing it')
}
// Only a first-ever delegation can assume zero. For a previously revoked
// delegation, reinstall the implementation first and read its retained nonce.
const batchNonce = !code || code === '0x' ? 0n : await publicClient.readContract({
  address: owner.address, abi: accountAbi, functionName: 'nonce',
})
const block = await publicClient.getBlock()
const deadline = block.timestamp + 300n
const funding = calls.reduce((total, call) => total + call.value, 0n)
const signature = await owner.signTypedData({
  domain: {
    name: 'TradingAccount7702', version: '1', chainId,
    verifyingContract: owner.address,
    salt: padHex(implementation, { size: 32 }),
  },
  primaryType: 'Batch',
  types: {
    Call: [
      { name: 'target', type: 'address' },
      { name: 'value', type: 'uint256' },
      { name: 'gasLimit', type: 'uint256' },
      { name: 'data', type: 'bytes' },
    ],
    Batch: [
      { name: 'calls', type: 'Call[]' },
      { name: 'nonce', type: 'uint256' },
      { name: 'deadline', type: 'uint256' },
      { name: 'relayer', type: 'address' },
      { name: 'funding', type: 'uint256' },
    ],
  },
  message: { calls, nonce: batchNonce, deadline, relayer: sponsor.address, funding },
})

// First use only. The sponsor submits the transaction, so omit executor: 'self'.
const authorization = await ownerClient.signAuthorization({
  account: owner, contractAddress: implementation,
})
const sponsoredHash = await sponsorClient.sendTransaction({
  account: sponsor,
  to: owner.address,
  authorizationList: [authorization], // Omit once already delegated.
  value: funding,
  data: encodeFunctionData({
    abi: accountAbi, functionName: 'executeSigned',
    args: [calls, batchNonce, deadline, sponsor.address, signature],
  }),
})
```

Use `batchDigest(...)` on the delegated EOA to compare client EIP-712 hashing
with the contract. Use the **EOA's** `nonce()`, not the implementation's. This
application nonce is independent of both the normal transaction nonce and
the EIP-7702 authorization nonce. Serialize outstanding batches for an account.
Passing zero as `relayer` permits any sponsor; the relayer value is itself signed.

## Cancellation and failure behavior

Every successful batch, including a self-paid one, advances the application
nonce. The EOA can send itself `invalidateNonce(newNonce)` with a strictly higher
nonce to cancel older pending signatures. Replacing this implementation with
another deployment retains the ERC-7201 nonce storage and changes the EIP-712
domain salt, so signatures for the previous implementation cannot be reused.
Clearing delegation does not clear the EOA's storage; reinstalling this
implementation resumes the retained nonce. Review existing delegations and
storage compatibility before replacing any other wallet implementation.

Execution is atomic. A reverted call, invalid signature, insufficient call gas,
or other execution failure reverts the entire batch, including USDC approvals,
trades, and the application nonce. The sponsor still pays transaction gas.
The EIP-7702 authorization is processed separately: delegation can remain
installed even when transaction execution reverts. Check account code after
a failed first-use transaction before retrying.

The executor has no public initializer, uses EOA-key signature recovery,
rejects recursive execution and batch calls to itself, and never uses
`delegatecall` to a market. It authorizes arbitrary calls chosen by the EOA;
it does not enforce a market allowlist. A batch signature can authorize asset
transfers as well as trades, so wallets must display the complete batch.
As with all EIP-7702 implementations, account delegation grants code control
over the EOA; review and audit the implementation before production use.
